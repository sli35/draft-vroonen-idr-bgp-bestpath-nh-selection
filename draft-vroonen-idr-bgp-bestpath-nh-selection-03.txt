             BGP best path next-hop selection enhancements
             draft-vroonen-idr-bgp-bestpath-nh-selection-03

Abstract

   BGP [RFC4271] has originally been designed to carry IPv4 routing
   information over the Internet.  IP routing being "hop-by-hop" in
   nature, NEXT_HOP which purpose is to carry the address of the next
   router to send the IP packet to.  In BGP, the next-hop may not be a
   directly connected router, hence, when evaluating paths, a BGP
   speaker must determine if the next-hop is resolvable and, if so,
   determine the internal cost to reach it.

   The incremental use of tunneling technologies to carry traffic
   between routers (e.g.: GRE, MPLS, SR-MPLS, SRv6...) may violate the
   assumption that the address carried in the NEXT_HOP is representative
   of the actual forwarding next-hop.  These technologies decouple the
   BGP control-plane's view of the next-hop from the data-plane's actual
   forwarding endpoint.  This document describes the problems that arise
   from this decoupling.  These problems include sub-optimal path
   selection, incorrect resolvability tracking of the forwarding path
   leading to traffic drop or misrouting, and others.  This document
   specifies how BGP uses path-resolution results and associated local
   policy as inputs to BGP path selection and how changes to those
   inputs are tracked.

1.  Introduction

   BGP [RFC4271] is designed to exchange network reachability
   information between routing domains.  A BGP update typically contains
   a prefix and a set of path attributes, including NEXT_HOP.  The
   receiving router uses this next-hop address to determine the egress
   point for traffic destined for the advertised prefix.  The underlying
   assumption is that the next-hop address represents the actual next
   router in the data plane's forwarding path.

   [RFC4271] Section 9.1.2.1 defines the route resolvability condition:
   a BGP route is considered unresolvable if the BGP speaker's routing
   table has no route matching the BGP route next-hop address.  As per
   [RFC4271] Section 9.1.2.2 e), when comparing paths received via
   internal BGP (IBGP), the metric to reach the BGP route's next-hop
   address, found in the routing table, is used to determine the best
   path.

                       AS 1
         <--------------------------------->

              +------+
       P/m  --| RTR1 |----------------+
              +------+ (N1, metric=1) |
                                      |
                                 +------+
                                 | RTR3 |
                                 +------+
                                      |
              +------+ (N2, metric=2) |
       P/m  --| RTR2 |----------------+
              +------+


                                  Figure 1

   In Figure 1, RTR3 receives prefix P/m from RTR1 and RTR2 (IBGP peers)
   with NEXT_HOP N1 and N2.  RTR3 resolves N1 with a cost of 1 and N2
   with a cost of 2.  Based on [RFC4271] procedures, RTR3 will select
   the path with the lowest cost to the NEXT_HOP address, so RTR3 will
   select the path received from RTR1.  In this example, the path used
   to resolve N1 and N2 reflects the actual forwarding path, which makes
   RTR3's best-path decision accurate.

   This document describes cases where the NEXT_HOP used in the BGP
   update is not representative of the actual forwarding path.  In these
   cases, the resolvability condition may fail in its goal and path
   selection may be done on inaccurate criteria leading to suboptimal
   routing, network congestion, traffic drop or misrouting...

   These use cases are not new and may have been partially addressed by
   IETF standards or drafts, some references are provided below:

   *  [I-D.ietf-idr-bgp-bestpath-selection-criteria] addresses the case
      of MPLS networks and proposes a modification of the route
      resolvability condition to be performed using forwarding database
      of a particular data plane protocol.  It also proposes an optional
      data path verification.

   *  [RFC9012] Section 7 improves the route resolvability condition by
      verifying that there is a feasible tunnel.  However, it doesn't
      take into account that the cost associated with the tunnel may be
      different from the cost associated with the BGP next-hop.

   *  [RFC9252] defines SRv6 overlay services signaling using BGP.  The
      procedures involve the advertisement of an SRv6 Service TLV within
      the BGP Prefix SID attribute to signal the SID to be used for
      forwarding.  RFC9252 highlights that ingress PE must perform a
      resolvability check for the SRv6 SID in addition to the
      resolvability check done on the NEXT_HOP.  However, it doesn't
      take into account that the cost associated with the SRv6 SID may
      be different from the cost associated with the BGP next-hop.

   This document defines a common path-resolution model for these use
   cases.  Each candidate path is associated with a path resolution
   tuple whose resolution provides inputs to BGP route selection.  BGP
   uses these inputs to compare candidate paths and tracks resolution
   changes that may require the selection to be reevaluated.

   In Figure 2, an IPv4 unicast service is deployed over a BGP-free MPLS
   core.  Let's assume PE3 receives prefix P/m from PE1 and PE2 with
   NEXT_HOP N1 and N2.  The existence of a route in PE3's IPv4 routing
   table to reach N1 or N2 (defined in [RFC4271]) is not sufficient to
   ensure that traffic can be carried from PE3 to PE1 or PE2.  PE3 needs
   to ensure that there is a tunnel available to reach PE1 or PE2 that
   can carry MPLS traffic (e.g.: an MPLS Label Switched Path (LSP)).  By
   checking only for the existence of a route in its routing table, PE3
   could create a traffic drop or misrouting if there is no tunnel to
   carry the IPv4 unicast traffic.  This use case is also considered in
   [I-D.ietf-idr-bgp-bestpath-selection-criteria].

2.2.  Segment Routing Traffic Engineering Policy

   When using SR Policies [RFC9256], the BGP NEXT_HOP may not accurately
   represent the actual forwarding path.  When SR Policy candidate paths
   are distributed via BGP [RFC9830], the metric of their segment lists
   can be carried as specified in [I-D.ietf-idr-sr-policy-metric],
   allowing the SR Policy metric to be taken into account in the best-
   path selection.

   In Figure 2, a BGP VPN service (as defined in [RFC4364]) is deployed
   between the PEs.  Let's assume PE3 receives prefix P/m from PE1 and
   PE2 with NEXT_HOP N1, N2 and color C1.  On PE3, SR Policies (C1, N1)
   and (C1, N2) are configured to use the low latency path.

   *  Costs M in parentheses represents cost of IGP.

   *  Costs D in brackets represents cost of latency-based metric

   If PE3 performs next-hop resolution based solely on the BGP NEXT_HOP,
   it will not verify the existence and state of a corresponding SR
   Policy (C1, Nx).  Consequently, it may select a suboptimal path by
   considering the cost to the NEXT_HOP address instead of the cost of
   the SR policy.  The best path considering SR-policy (C1, Nx) cost is
   via PE2, while the best path considering IGP metric is via PE1.

                       +========+==========+======+
                       | Prefix | Next hop | Cost |
                       +========+==========+======+
                       | N1     | P1       | 2    |
                       +--------+----------+------+
                       | N2     | P1       | 6    |
                       +--------+----------+------+

                               table of PE3

                  +===========+==========+======+=======+
                  | SR Policy | Next hop | Cost | State |
                  +===========+==========+======+=======+
                  | (C1, N1)  | P1       | 12   | Up    |
                  +-----------+----------+------+-------+
                  | (C1, N2)  | P2       | 4    | Up    |
                  +-----------+----------+------+-------+

                        Table 2: SR Policies of PE3

   Considering that PE3 may take into account the cost of the SR policy
   and then picks up the path from PE2 as best.  If the SR Policy (C1,
   N2) is down or not present, and considering that color C1 uses Color-
   Only Type 0 (bits 00), as defined in [RFC9830] Section 3, the
   steering procedures in [RFC9256] Section 8.8.1 authorize the path
   from PE2 to use the IGP path to next-hop N2 (fallback to the IGP path
   via P1 with cost=6) when there is no policy (C1, N2) available.  This
   situation has multiple drawbacks:

   *  The costs of the two BGP paths are not directly comparable, which
      makes the comparison inaccurate: the path via PE1 uses a latency-
      based cost, while the fallback path via PE2 uses an IGP metric.

   *  Using a path without an SR-policy may violate the intent of the
      service, especially if there is an alternate path (from PE1) that
      fulfills the intent.

   It may be desirable for PE3 to prefer the path from PE1 that
   satisfies color C1 or even exclude any path that does not meet the
   color C1 requirement.

2.3.  SRv6 services

   When using SRv6 services as defined in [RFC9252], the BGP NEXT_HOP
   may not be representative of the actual forwarding path.

   Considering Figure 2, an SRv6-based BGP VPN is deployed between the
   PEs.  PE1 uses locator L1 for algorithm 0 and L1_FA for flexible
   algorithm 128 ([RFC9350]) optimized for low-latency.  Similarly, PE2
   uses locator L2 for algorithm 0 and L2_FA for flexible algorithm 128.
   Let's assume PE3 receives prefix P/m from PE1 and PE2 with NEXT_HOP
   N1, N2 and SRv6 SID S1 and S2.  SID S1 and S2 are allocated
   respectively from L1_FA and L2_FA.

   *  Costs M in parentheses represents cost of algorithm 0 (as defined
      in [RFC8665] Section 8.5).

   *  Costs D in brackets represents cost of flexible algorithm
      [RFC9350] 129 which is using low-latency metric.

   The IPv6 routing table of PE3 contains the following entries:

                       +========+==========+======+
                       | Prefix | Next hop | Cost |
                       +========+==========+======+
                       | N1     | P1       | 2    |
                       +--------+----------+------+
                       | N2     | P1       | 6    |
                       +--------+----------+------+
                       | L1     | P1       | 2    |
                       +--------+----------+------+
                       | L2     | P1       | 6    |
                       +--------+----------+------+
                       | L1_FA  | P1       | 12   |
                       +--------+----------+------+
                       | L2_FA  | P2       | 4    |

   Based on [RFC4271] procedures, PE3 verifies that NEXT_HOP address of
   each path is resolvable.  Based on [RFC9252] procedures, PE3 verifies
   that S1 and S2 addresses are resolvable.  PE3 will then select the
   path with the lowest cost to the NEXT_HOP address according to
   [RFC4271] .  Cost to N1 is lower than cost to N2, so PE3 will select
   the path received from PE1.  However, from a latency perspective,
   path to PE2 is the best one.

   The problem of path suboptimality may also happen with algorithm 0,
   if for instance SRv6 traffic for algorithm 0 needs to be offloaded
   from PE1, operator may increase the metric of the locator (while not
   changing the metric of the next-hop) on PE1.  In the example above,

3.  Path Resolution Inputs to BGP Route Selection

3.1.  Path resolution tuple

   This document defines a path resolution tuple as a resolution key
   and, when required, a resolution context.  The resolution key
   identifies the object to be resolved for a BGP path.  For the
   mechanisms defined in this document, the resolution key is an IP
   address.  It may be the BGP NEXT_HOP or a different address signaled
   with the path, such as a Tunnel Egress Endpoint or an SRv6 Service
   SID.

   The following data already defined in BGP standards SHOULD be
   considered as resolution keys:

   *  The Tunnel Egress Endpoint Sub-TLV contained in Tunnel
      Encapsulation attribute defined in [RFC9012]

   *  SRv6 SID Information Sub-TLV contained within L3 or L2 SRv6 SID
      defined in [RFC9252]

   Unless a BGP update contains another type of resolution key, the BGP
   NEXT_HOP is considered as the resolution key.

   The resolution key MAY be complemented by a resolution context.  When
   present, the resolution context identifies or parameterizes the
   resolution procedure and datastore used to resolve the resolution
   key.  The following attributes defined in BGP standards are examples
   of resolution contexts:

   *  The Tunnel Encapsulation attribute defined in [RFC9012]

   *  The Color extended community defined in [RFC9012]

   *  The SRv6 Sub-TLV and Sub-sub-TLV contained within L3 or L2 SRv6
      SID TLV as defined in [RFC9252] other than the SID itself






Vroonen, et al.          Expires 7 January 2027                 [Page 8]

Internet-Draft        BGP nh selection enhancements            July 2026


   Two path resolution tuples containing the same resolution key but
   differing in resolution context, including whether a context is
   present, are distinct resolution requests.  For example, in the SR
   Policy use case above, {N1, C1} requests resolution through SR Policy
   (C1, N1), whereas {N1} requests resolution of next hop N1 without a
   route-carried resolution context.

   Each new BGP extension SHOULD specify whether an address carried by
   the extension is a resolution key and, when applicable, how its
   resolution context is derived.  The procedures defined in the next
   section SHOULD apply for any new resolution key without having to
   redefine them.

3.2.  Resolution constraints

   When a path resolution tuple is identified for a BGP route, the
   resolver uses the resolution key together with its resolution
   context, when present.  Resolution constraints are rules applied when
   resolving a path resolution tuple.  They restrict which routes or
   datastores may provide a valid resolution.  These constraints are not
   additional components of the path resolution tuple and may be derived
   from the resolution context or configured locally.

   In some cases, an operator may want to enforce that the resolution
   key is resolved through a specific type of route.  This can be
   achieved by configuring a local resolution constraint.  Reusing the
   example defined in Section 2.1, if we consider an IPv4 unicast BGP
   service carried over a BGP free-core, the BGP NEXT_HOP must be
   reachable through a tunnel to allow the end-to-end packet delivery.
   Such a case cannot be derived from the BGP update context and BGP
   must be configured to resolve the NEXT_HOP only through tunnels (of
   any or specific types).  Similarly, when aggregate routes are present
   in the routing table, a user may want to prevent a resolution key
   that identifies a more-specific destination from being resolved over
   an aggregate route.  A resolution constraint based on prefix/mask can
   be used to prevent such a resolution from being considered valid.  An
   implementation MAY provide a set of configuration options for
   resolution constraints.

   Another example of a resolution constraint is the "Resolution
   Scheme", defined in BGP Classful Transport [RFC9832].  The
   "Resolution Scheme" constrains the resolution of the NEXT_HOP to an
   ordered set of transport classes dictated by the intent (Mapping
   Community) attached to the route.

3.3.  Path-resolution result and preference

   Path-resolution result:
      The outcome of resolving a path resolution tuple subject to the
      applicable resolution constraints.  It indicates whether
      resolution succeeded.  When resolution succeeds, the result
      identifies the resolution actually selected, including any
      fallback, and provides any available metric, forwarding
      information, and information needed to track changes.  Each
      successful result used by the replacement route-selection
      procedure defined below is associated with a path-resolution
      preference.

   Path-resolution preference:
      A locally significant value that orders the resolution outcomes
      represented by path-resolution results.  For any two preference
      values used in the same comparison, either the values are
      identical or the locally defined ordering MUST identify exactly
      one value as preferred to the other.  The ordering MUST be
      consistent: if preference A is preferred to preference B and
      preference B is preferred to preference C, preference A MUST be
      preferred to preference C.  The representation of a path-
      resolution preference and the source of its ordering are
      implementation matters.  An implementation can derive the value
      from properties of the result or from local policy and can
      represent it numerically.  This document does not require a
      numeric representation and does not specify whether a lower or a
      higher numeric value is more preferred.  A path-resolution
      preference is not a BGP path attribute and is not advertised.

   When the replacement route-selection procedure defined below is
   enabled, each path-resolution result under consideration for the same
   destination MUST be assigned a path-resolution preference from the
   same local ordering.  Metrics provided by results assigned the same
   path-resolution preference MUST have common comparison semantics and
   use the same ordering.  Results whose metrics cannot be meaningfully
   compared MUST be assigned different path-resolution preferences.  For
   any two metrics provided by results assigned the same preference, the
   comparison MUST return exactly one of the following outcomes: the
   first metric is preferred, the second metric is preferred, or the
   metrics are equivalent.  The comparison MUST be consistent: if metric
   A is preferred to metric B and metric B is preferred to metric C,
   metric A MUST be preferred to metric C; if metric A is equivalent to
   metric B and metric B is equivalent to metric C, metric A MUST be
   equivalent to metric C.






Vroonen, et al.          Expires 7 January 2027                [Page 10]

Internet-Draft        BGP nh selection enhancements            July 2026


   The path-resolution preference used for comparison MUST be associated
   with the resolution actually selected, including any fallback
   resolution.  For example, when an intent-aware resolution falls back
   to best-effort transport, the applicable preference is the one
   associated with the selected best-effort result, not with the
   requested intent.  The resolvability, selected resolution, path-
   resolution preference, metric, forwarding information, and tracking
   information used for a BGP path MUST all pertain to the same path-
   resolution result.  An implementation MUST NOT combine inputs
   associated with different path-resolution results as if they
   described the same resolution.

3.4.  Route resolvability condition

   This document updates [RFC4271] Section 9.1.2.1 as follows:

   *  The route resolvability check for the BGP NEXT_HOP MUST continue
      to be done.

   *  The additional path resolution tuple resolvability check MAY be
      enabled through local configuration.  When enabled, the path
      resolution tuple MUST be resolved subject to the applicable
      resolution constraints defined in Section 3.2.  A route whose path
      resolution tuple cannot be resolved under those constraints MUST
      be treated as unresolvable.

3.5.  Path-resolution preference and internal cost determination

   For a prefix P/m, different BGP paths may use different path
   resolution tuples.

         P/m
             Path1: NH=10.0.0.1 Color: 200
             Path2: NH=2001::2 SRv6-SID: cafe:0:2:e002::
             Path3: NH=10.0.0.3 Tunnel-encap(L2TPv3, endpoint: 10.0.0.3)
             Path4: NH=2001::4 SRv6-SID: cafe:0:4:e002::

                                Figure 3

   Metrics returned by different path-resolution results are not
   necessarily comparable because they can have different semantics or
   can be produced by different resolution procedures.  For instance,
   Path1 can use an SR Policy that optimizes for latency, while Path2
   can use an IGP metric and Path3 can have no metric.  The numeric
   values associated with these results cannot be assumed to be
   comparable.





Vroonen, et al.          Expires 7 January 2027                [Page 11]

Internet-Draft        BGP nh selection enhancements            July 2026


   The need to distinguish metrics with different semantics is not new.
   A prefix can have BGP paths whose next hops are resolved by different
   IGPs or route types.  Even when each resolution provides a numeric
   metric, comparing the values without common comparison semantics can
   produce an incorrect ordering.

   When enabled, the following procedure replaces step e) of [RFC4271]
   Section 9.1.2.2.  For this procedure, the interior cost is obtained
   only from the path-resolution result.  A metric obtained from the
   independently required BGP NEXT_HOP resolution MUST NOT be used as an
   additional or alternative interior cost.

   When this replacement procedure is enabled, the additional path
   resolution tuple resolvability check defined in Section 3.4 MUST also
   be enabled.  A path whose path resolution tuple is unresolvable MUST
   be removed from consideration before it reaches this procedure.

   *  Retain only candidate paths whose path-resolution preference is
      the most preferred among the candidate paths.

   *  Compare the metrics provided by the remaining path-resolution
      results using their common metric ordering.  An absent metric MUST
      compare less preferred than every available metric and equivalent
      to another absent metric.  Retain only paths whose metric is most
      preferred.  Metrics that compare equivalently do not distinguish
      paths.  If no remaining result provides a metric, skip the
      interior-cost comparison.  This rule does not require an
      implementation to assign a numeric value to an absent metric.

   To support controlled deployment and rollback, an implementation
   SHOULD provide local configuration to enable or disable the
   replacement procedure defined in this section.  When the replacement
   procedure is disabled, the unmodified procedure in [RFC4271]
   Section 9.1.2.2 e) applies.

   The following example applies this procedure to the four paths shown
   above.  Local policy assigns preference Tier-A to results that
   resolve through an SRv6 SID, Tier-B to results that resolve through
   an SR Policy, and Tier-C to results that resolve through L2TPv3.
   Tier-A is preferred to Tier-B, which is preferred to Tier-C.  Metrics
   provided by the Tier-A results use the same IGP metric semantics and
   can be compared.  The labels and their ordering are local to this
   example.  An implementation can represent the ordering numerically,

3.6.  Next hop and path resolution tracking

   For every path to which these procedures apply, a BGP speaker MUST
   maintain sufficient dependency information to detect changes in each
   applicable input: BGP NEXT_HOP resolvability; path resolution tuple
   resolvability or selected resolution; assigned path-resolution
   preference; and metric presence or value.  Dependency tracking MUST
   distinguish path resolution tuples that have the same resolution key
   but different resolution contexts, including the absence of a
   resolution context.

   A change to any dependency listed above MUST cause best-path
   selection to be re-evaluated for every destination having a path that
   depends on the affected BGP NEXT_HOP or path resolution tuple.  Any
   change to local policy or configuration that alters the derivation or
   comparison of path-resolution results MUST cause best-path selection
   to be re-evaluated for every destination having a path to which the
   change applies.  This includes changes to resolution constraints,
   resolution-selection or fallback policy, procedure enablement,
   preference assignment or ordering, metric ordering, or metric
   comparability.

   These requirements apply to selected and non-selected paths.

   PE3, with NEXT_HOP N1, N2, and N3, respectively.  Because the network

   RSVP-TE provides traffic-engineered MPLS tunnels, while SR-MPLS
   provides best-effort reachability.  PE4 uses a local resolution
   procedure that selects RSVP-TE when it is available and otherwise
   falls back to SR-MPLS.  The RSVP-TE tunnel to PE3 cannot be
   established.

   results are not compared with RSVP-TE metrics because the results
   have different path-resolution preferences.

5.  Example with Intent-Aware BGP Transport

   This example illustrates how local policy can order path-resolution
   results when intent-aware BGP transport is deployed.  Both BGP
   Classful Transport ([RFC9832]) and BGP Color-Aware Routing
   ([RFC9871]) can produce candidate paths that are resolved through
   different transport mechanisms whose metrics are not directly
   comparable.  The preference names used below are illustrative local

   values.

                        +-----+     (M=5)
                P/m  -- | PE1 |----------------+
                 (N1)   +-----+                |
                                             +----+     (M=5)    +-----+
                                             | P1 |--------------| PE3 |
                                             +----+              +-----+
                        +-----+     (M=10)    |
                P/m  -- | PE2 |----------------+
                 (N2)   +-----+

   In Figure 6, PE3 receives a VPN prefix P/m from PE1 and PE2 with
   NEXT_HOP N1 and N2 respectively.  An intent-aware transport
   technology is deployed, requesting "Gold" SLA transport for this
   prefix.  Gold RSVP-TE tunnels exist from PE3 to PE1 but not from PE3
   to PE2.  Best-effort SR-MPLS tunnels exist to both PE1 and PE2.

   In a BGP Classful Transport ([RFC9832]) deployment, P/m is advertised
   with Color Extended Community color:0:100 acting as a Mapping
   Community for the Gold transport intent.  The Mapping Community maps
   the service route to a Resolution Scheme containing the ordered TRDB
   list [TRDB-Gold, TRDB-Best-Effort].  Following [RFC9832] Section 7.8,
   the Resolution Scheme uses those TRDBs in order to resolve the BGP
   NEXT_HOP of each path:

   *  Path1 (NH=N1): a matching Tunnel Route for endpoint N1 is found in
      the primary TRDB, TRDB-Gold, and uses the RSVP-TE tunnel to PE1.

   *  Path2 (NH=N2): no matching Tunnel Route for endpoint N2 is found
      in TRDB-Gold.  A matching Tunnel Route is found in the backup
      TRDB, TRDB-Best-Effort, and uses the SR-MPLS tunnel to PE2.

   In a BGP Color-Aware Routing ([RFC9871]) deployment, P/m is
   advertised as a service route carrying BGP Color Extended Community
   C_Gold.  Following the service-steering procedures in [RFC9871]
   Section 3, PE3 attempts to steer traffic for each service path over
   the corresponding color-aware path:

   *  Path1 (NH=N1): the color-aware path (N1, C_Gold), backed by RSVP-
      TE, is available and is selected.

   *  Path2 (NH=N2): no color-aware path (N2, C_Gold) is available.
      Local service-steering policy permits fallback to a color-unaware
      best-effort path backed by SR-MPLS.

   Routing service steering select different types of objects, their

   model defined in this document.  The selected object and resulting

   PE3's local policy assigns the path-resolution preference shown
   below.

   In this example, local policy treats Gold as the requested transport
   property and best-effort as a permitted degraded fallback.  It
   assigns the path-resolution preference Preferred-Transport to a

6.  Operational Considerations

   In most cases, tunnels carry traffic from the ingress to the egress
   node that advertised the BGP service route, as transit routers are
   not aware of the BGP service routes.  For instance, in SRv6 service
   cases, the SRv6 encapsulation using the advertised SID as destination
   carries traffic down to the node that knows about the service route.
   Using the metric in the path-resolution result for the selected
   resolution as the internal cost makes sense in these cases because
   the selected resolution describes the end-to-end forwarding path.

   However, there are cases where the tunnel does not terminate on the
   service egress.  One example is a service route advertised with a
   color allowing for usage of a null endpoint policy.  Another example
   is a service route advertised with a Tunnel Encapsulation attribute
   using a tunnel endpoint different from the service egress.  In such
   cases, the tail node of the tunnel must have routing entries for the
   service routes to ensure end-to-end reachability.

   In these cases, the metric in the path-resolution result for the
   selected resolution may not reflect the end-to-end path.  The
   independently required NEXT_HOP resolution is not a second internal-
   cost input.  Even if its metric were substituted, it would not
   necessarily provide a better view: it would still give an inaccurate
   picture of distances from a traffic forwarding perspective, since the
   forwarding path does not follow the IGP-routed path.  Additionally,
   operators commonly manipulate the NEXT_HOP through routing policies,
   so there is no guarantee that the NEXT_HOP address correctly reflects
   the real egress node.  Hence, the metric in the path-resolution



Vroonen, et al.          Expires 7 January 2027                [Page 19]

Internet-Draft        BGP nh selection enhancements            July 2026


   result for the selected resolution when the tunnel tail is not the
   service egress is no less representative than such a hypothetical
   NEXT_HOP-derived metric.

   This document specifies path-resolution inputs used by BGP route
   selection, including resolvability, path-resolution preference, and
   the metric associated with the selected result, when available.
   Consequently, the potential impact on routing loops needs to be
   analyzed.

   The mechanisms described in this document are typically deployed in
   environments utilizing tunneling technologies (such as MPLS or SRv6).
   In these scenarios, BGP path selection determines the path resolution
   tuple whose resolution supplies the forwarding information used for
   encapsulation.

   When the traffic is encapsulated at the ingress router, intermediate
   nodes forward packets based solely on the outer transport header
   rather than the inner destination.  Consequently, the specific BGP
   selection criteria are enforced only at the ingress, preventing
   forwarding loops that might otherwise arise from inconsistent policy
   decisions on intermediate nodes.

   To illustrate this loop prevention, consider the following topology
   where PE1, PE2, and PE3 provide reachability to Prefix X.

                             +-------+
                           /|  PE2  |--- Prefix X
                 (Low Delay) |       |
                           / +-------+
                         /
       +-------+    +-------+
       |  PE1  |----|   P   |
       +-------+    +-------+
       (Ingress)          \
                           \ +-------+
                 (Low IGP)   |  PE3  |--- Prefix X
                             |       |
                             +-------+

                Figure 8: Loop Prevention via Encapsulation

   Assume PE1 is configured with the mechanisms defined in this document
   and selects PE2 as the BGP next-hop for Prefix X to optimize for low
   delay.  Router P is a transit node and uses standard BGP procedures,
   preferring PE3 due to a lower IGP metric.





Vroonen, et al.          Expires 7 January 2027                [Page 20]

Internet-Draft        BGP nh selection enhancements            July 2026


   In a hop-by-hop IP routing paradigm, PE1 would forward a bare IP
   packet to P.  Router P would perform a lookup on the inner
   destination IP (Prefix X) and deflect the packet toward PE3, directly
   contradicting PE1's decision and potentially causing a loop if PE3
   also had a conflicting policy.

   However, in a tunneling paradigm, PE1 encapsulates the packet with an
   outer header (e.g., an SRv6 SID or MPLS label) using forwarding
   information returned by resolution of the selected path's path
   resolution tuple.  When the packet arrives at Router P, P only
   evaluates the outer header and forwards the packet along the IGP
   shortest path to PE2.  Router P's BGP policy regarding Prefix X is
   never invoked for in-flight traffic.

   Nevertheless, to ensure predictable routing behavior and simplify
   troubleshooting, it is recommended that network operators maintain
   consistent semantics for assigning and ordering path-resolution
   preferences and for comparing metrics between results assigned the
   same preference across all BGP speakers under the same
   administration.  Because path-resolution preferences are locally
   significant, their internal representations need not be identical
   across speakers.

7.  Relationship to draft-ietf-idr-bgp-bestpath-selection-criteria

   This document and [I-D.ietf-idr-bgp-bestpath-selection-criteria] are
   complementary.  Their relationship can be summarized as follows:

   *  Scope: [I-D.ietf-idr-bgp-bestpath-selection-criteria] performs the
      resolvability check only; this document also covers path-
      resolution preference, metric comparability, and internal cost
      determination.

   *  Generality: [I-D.ietf-idr-bgp-bestpath-selection-criteria] is
      MPLS-centric; this document is generic and applies to MPLS, SR
      Policy, SRv6 and intent-aware BGP transport.

   *  This document introduces the path resolution tuple, comprising a
      resolution key and an optional resolution context, while
      continuing to require BGP NEXT_HOP resolvability.

   *  This document introduces path-resolution preference to order
      resolution results before the interior-cost comparison and
      requires any metrics provided by results assigned the same
      preference to have common comparison semantics.






Vroonen, et al.          Expires 7 January 2027                [Page 21]

Internet-Draft        BGP nh selection enhancements            July 2026


   *  This document derives the internal cost only from resolution of
      the path resolution tuple.  The independently required BGP
      NEXT_HOP check contributes resolvability, not a second cost.

   *  The MPLS case covered by
      [I-D.ietf-idr-bgp-bestpath-selection-criteria] is one instance of
      the generic mechanism defined here.

9.  Security Considerations

   This document does not define any new information exchanged between
   BGP speakers.  Path-resolution preferences are purely local and are
   not advertised.

   BGP attributes that contribute to a resolution key or resolution
   context can influence the selected path-resolution result and,
   consequently, BGP route selection.  Existing validation and policy
   controls for those attributes continue to apply.  Incorrect or
   unauthorized preference assignment or ordering can steer traffic
   through an unintended resolution.  Assigning the same preference to
   results whose metrics do not have common comparison semantics can
   cause unlike metrics to be compared.  Configuration of these local
   policies needs the same protection against unauthorized modification
   as other local routing policy.
